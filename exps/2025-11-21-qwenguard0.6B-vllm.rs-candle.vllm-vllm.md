# Qwen3Guard vLLM Benchmark

This repository contains benchmarks for testing Qwen3Guard model performance using vLLM and candle-vllm inference servers. The benchmarks measure throughput, latency, and accuracy under various concurrency levels.

## Overview

The benchmark suite includes:
- **vLLM Benchmark**: Tests Qwen3Guard via vLLM HTTP endpoint
- **candle-vllm Benchmark**: Tests Qwen3Guard via candle-vllm HTTP endpoint
- **Sequential Benchmark**: Tests Qwen3Guard using direct model inference (for comparison)

## Prerequisites

- Rust toolchain (cargo, rustc)
- CUDA-capable GPU
- vLLM or candle-vllm installed and configured
- Qwen3GuardTest dataset

## Environment Variables

Set the dataset path as an environment variable:

```bash
export QWEN3_GUARD_DATASET_PATH=/path/to/Qwen3GuardTest
```

## Starting the Server

### Option 1: vLLM Server

```bash
# Set CUDA device (optional, adjust device number as needed)
export CUDA_VISIBLE_DEVICES=3

# Start vLLM server
vllm serve Qwen/Qwen3Guard-Gen-0.6B
```

The server will start at `http://localhost:8000/v1/` by default.

### Option 2: candle-vllm Server

```bash
# Set CUDA device (optional, adjust device number as needed)
export CUDA_VISIBLE_DEVICES=2

# Start candle-vllm server
target/release/candle-vllm --m Qwen/Qwen3Guard-Gen-0.6B --p 8000
```

The server will start at `http://localhost:8000/v1/` (or the specified port).

## Running the Benchmark

### Basic Usage

```bash
# Set dataset path (adjust path as needed)
export QWEN3_GUARD_DATASET_PATH=/path/to/Qwen3GuardTest

# Run benchmark
cargo run --release --example qwen3_guard_vllm_benchmark -- \
    --endpoint http://localhost:8000/v1/chat/completions \
    --model Qwen/Qwen3Guard-Gen-0.6B \
    --dataset-path $QWEN3_GUARD_DATASET_PATH \
    --split thinking \
    --max-samples 100 \
    --concurrency 1,2,4,8,16,32,64
```

### Command-Line Arguments

- `--endpoint` (required): vLLM endpoint URL
  - Example: `http://localhost:8000/v1/chat/completions`
  
- `--model` (required): Model name
  - Example: `Qwen/Qwen3Guard-Gen-0.6B`

- `--dataset-path` (required): Path to Qwen3GuardTest dataset directory
  - Should contain JSONL files like `thinking.jsonl`, `thinking_loc.jsonl`, etc.

- `--split` (optional): Dataset split to use
  - Options: `thinking`, `thinking_loc`, `response_loc`
  - Default: `thinking`

- `--max-samples` (optional): Maximum number of samples to test
  - Default: all samples in the dataset

- `--concurrency` (optional): Comma-separated concurrency levels
  - Default: `1,2,4,8`
  - Example: `--concurrency 1,2,4,8,16,32,64`

### Benchmark Versions

There are two versions of the vLLM benchmark:

1. **Standard Version** (`qwen3_guard_vllm_benchmark`): Uses manual prompt formatting
   - Accuracy: ~78%
   - Uses combined text with classification instructions

2. **Messages Version** (`qwen3_guard_vllm_benchmark_messages`): Uses original message structure
   - Expected accuracy: ~84% (matches sequential benchmark)
   - Uses original messages array, letting vLLM apply chat template automatically

To use the messages version:

```bash
# Set dataset path (adjust path as needed)
export QWEN3_GUARD_DATASET_PATH=/path/to/Qwen3GuardTest

# Run benchmark
cargo run --release --example qwen3_guard_vllm_benchmark_messages -- \
    --endpoint http://localhost:8000/v1/chat/completions \
    --model Qwen/Qwen3Guard-Gen-0.6B \
    --dataset-path $QWEN3_GUARD_DATASET_PATH \
    --split thinking \
    --max-samples 100 \
    --concurrency 1,2,4,8
```

## Results Comparison

### vLLM vs candle-vllm vs vllm-rs Performance Comparison

All three implementations were benchmarked using identical configurations:
- Model: `Qwen/Qwen3Guard-Gen-0.6B`
- Dataset: 100 samples from Qwen3GuardTest "thinking" split
- Concurrency levels: 1, 2, 4, 8, 16, 32, 64

**Note on vllm-rs configuration**: The vllm-rs server was configured with `--max-num-seqs 32 --max-model-len 4096` instead of `--max-num-seqs 64` due to memory limitations (setting 64 causes Out of Memory errors). Additionally, `--max-model-len` was set to 4096 instead of 2048 because some prompts in the dataset are longer than 2048 tokens.

#### Throughput Comparison (req/s) - Higher is Better

| Concurrency | vLLM      | candle-vllm | vllm-rs |
|-------------|-----------|-------------|---------|
| 1           | 10.12     | 1.52        | 0.49    |
| 2           | 25.24     | 4.96        | 0.98    |
| 4           | 42.86     | 7.91        | 1.94    |
| 8           | 67.74     | 9.14        | 3.70    |
| 16          | 93.37     | 9.88        | 5.99    |
| 32          | 116.85    | 9.57        | 8.13    |
| 64          | 134.40    | 9.60        | 9.28    |

**Result**: vLLM significantly outperforms candle-vllm and vllm-rs in throughput, with the advantage increasing with concurrency. At 64 concurrency, vLLM achieves 134.40 req/s, candle-vllm achieves 9.60 req/s, and vllm-rs achieves 9.28 req/s.

#### Average Latency Comparison (ms) - Lower is Better

| Concurrency | vLLM   | candle-vllm | vllm-rs  |
|-------------|--------|-------------|----------|
| 1           | 98.83  | 656.76      | 2037.73  |
| 2           | 39.62  | 201.62      | 1021.37  |

| 8           | 14.76  | 109.35      | 270.02   |
| 16          | 10.71  | 101.17      | 166.90   |
| 32          | 8.56   | 104.53      | 123.04   |
| 64          | 7.44   | 104.20      | 107.81   |

**Result**: vLLM has significantly lower latency than candle-vllm and vllm-rs (lower is better). At 64 concurrency, vLLM latency is 7.44ms, candle-vllm is 104.20ms, and vllm-rs is 107.81ms.

### Performance Analysis

**vLLM**: Scales well with concurrency, achieving **134.40 req/s** and **7.44ms latency** at 64 concurrency.

**candle-vllm**: Throughput plateaus early (~9.60 req/s), with **104.20ms latency** at 64 concurrency.

**vllm-rs**: Throughput scales up to **9.28 req/s** at 64 concurrency, with **107.81ms latency**.

### Accuracy Metrics

**Overall Accuracy: 78.00%** (consistent across all concurrency levels for both implementations)

#### Safe Class Performance
- **Precision**: 71.05%
- **Recall**: 100.00%
- All safe samples are correctly identified, but some unsafe samples are misclassified as safe

#### Unsafe Class Performance
- **Precision**: 100.00%
- **Recall**: 52.17%
- When the model predicts "unsafe", it's always correct, but it misses ~48% of unsafe samples

### Key Findings

1. **vLLM outperforms candle-vllm and vllm-rs**: At 64 concurrency, vLLM achieves 134.40 req/s (vs 9.60 req/s for candle-vllm and 9.28 req/s for vllm-rs) and 7.44ms latency (vs 104.20ms for candle-vllm and 107.81ms for vllm-rs).

2. **All three achieve identical accuracy**: 78.00% across all concurrency levels.

3. **vLLM scales better**: Throughput improves up to 64 concurrent requests, while candle-vllm and vllm-rs plateau around 8-16.

## Notes

- The benchmark uses the standard version (`qwen3_guard_vllm_benchmark`) which achieves 78% accuracy
- For higher accuracy (~84%), use the messages version (`qwen3_guard_vllm_benchmark_messages`)
- Results are based on 100 samples from the "thinking" split of Qwen3GuardTest dataset
- All tests were run with `max_tokens=128` and default sampling parameters

## Troubleshooting

1. **Connection refused errors**: Ensure the vLLM/candle-vllm server is running and accessible
2. **Model not found**: Verify the model path/name is correct
3. **Dataset not found**: Check the dataset path and ensure JSONL files exist
4. **Low accuracy**: Try using the messages version (`qwen3_guard_vllm_benchmark_messages`) for better accuracy
